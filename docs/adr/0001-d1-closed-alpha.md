# ADR 0001: D1 for the Phase 1 closed alpha

- Status: Accepted
- Date: 2026-07-20
- Owners: HANZI.OS engineering

This ADR records the architecture decision and hosting assumptions as of its
date. It does not attest that the retained Sites project, D1 resource or hosted
closed-alpha service is currently provisioned or reachable.

## Context

HANZI.OS Phase 0 keeps learning state in browser storage. Phase 1 requires
durable accounts, cross-device recovery, idempotent learning writes, offline
reconciliation, export and deletion. The target architecture names PostgreSQL,
while Sites on Cloudflare Workers was the selected deployment target when this
decision was accepted. The repository retains that target's configuration and
uses its logical D1 binding contract without database identifiers in source.
That dated target context is not evidence of a current hosted deployment.

Learning correctness is the controlling constraint. XP, streaks, lesson visits
and FSRS self-ratings are not mastery evidence. Attempts and evidence must keep
the content, activity, schema, scoring and policy versions that produced them.

## Decision

Adopt Cloudflare D1 through the logical `DB` binding as the Phase 1 closed-alpha
source-of-truth design and implementation path. It becomes an operational
source of truth only in a provisioned, verified hosted environment. Keep R2
disabled until a reviewed workflow requires durable audio or another blob.

The model uses:

- schema cho append-only attempts, evidence, review logs và XP ledger;
- revisioned cloud document được server merge/replay theo policy cho khả năng khôi phục closed alpha;
- unique, user-scoped idempotency records with request hashes;
- versioned course, activity, scoring, evidence-policy and FSRS references;
- a revisioned learning document for sync compatibility, backed by normalized
  records that can rebuild learning projections;
- a monotonic change feed plus durable import receipts;
- a transactional outbox for later observability and asynchronous consumers.

Authenticated ownership is always resolved on the server; client payload cannot
select a `user_id`. Server recomputes aggregate projections instead of accepting
aggregate mastery/XP fields verbatim. However, the generic snapshot sync endpoint
cannot independently re-grade every historical answer. Newly normalized imported
evidence therefore remains compatibility history until a version-aware command
endpoint verifies it; closed-alpha cloud recovery is not a production mastery
attestation. Draft and review content remain unavailable to navigation,
recommendation and progress denominators.

## Portability boundary

Application code will access persistence through repositories and transaction
services rather than importing a D1 binding in UI or route logic. Domain IDs are
text UUIDs, timestamps are epoch milliseconds, JSON is stored as text, and SQL
stays within the SQLite/PostgreSQL overlap where practical.

D1-specific details are isolated to:

- the Drizzle SQLite schema and generated migrations;
- the `DB` binding adapter;
- the implementation of atomic prepared-statement batches;
- the auto-incrementing sync cursor.

A PostgreSQL move will add a PostgreSQL Drizzle schema and repository adapter,
backfill immutable rows in dependency order, verify row counts and hashes, then
dual-read before cutover. Public IDs, idempotency keys and content/activity
versions remain unchanged, so clients and evidence history do not require an
identity rewrite.

## Local-to-cloud migration rules

- Import is identified by `(user_id, snapshot_hash)` and is retry-safe.
- Existing `skillMastery` values are not imported as evidence.
- Existing XP may be preserved as a versioned legacy ledger adjustment but can
  never unlock content or raise mastery.
- Legacy evidence is revalidated against its exact released content version.
  Evidence that cannot be reproduced is retained as unverified history and is
  excluded from mastery.
- FSRS state may seed scheduling but a self-rating remains ineligible for
  mastery.
- Browser data is not deleted until the server commit is acknowledged and a
  canonical snapshot plus sync cursor is durably stored on the device.

Implementation amendment (25 July 2026): the compatibility migration preserves
legacy XP and browser FSRS state only in the local snapshot. It deliberately
does not create a cloud XP ledger adjustment or seed server FSRS cards. Those
two earlier allowances are superseded because neither client-authored value is
acceptable authority for mastery, rewards, prerequisite release or review
timing. A future import requires a separately versioned, reviewed policy and
must remain mastery-ineligible unless independently verified.

## Migration and rollback policy

Schema migrations are generated by Drizzle, committed under `drizzle/`,
inspected as SQL, and packaged with the Sites artifact. Migrations are
forward-only. Destructive changes require an additive compatibility release,
verified backfill and a separate cleanup release. Application rollback must
continue reading the previous schema until that compatibility window closes.

Before an irreversible migration, create and verify a recoverable database
backup. The local restore rehearsal currently applies all nine committed
migrations, checks the 22-table graph, integrity, foreign keys and a post-restore
write. This is local technical coverage, not a hosted D1 backup/restore drill.
Hosted CI must also apply all migrations to an empty D1 database and exercise
retry, cross-user isolation, duplicate import and projection rebuild tests.

## Consequences

This decision provides a D1-capable durability path and keeps the Phase 1 slice
small enough for a closed alpha; local tests alone do not establish hosted
durability. D1 is not declared the permanent production database.
Authentication, sync APIs, a per-owner IndexedDB outbox, deterministic merge,
export and delete workflows are implemented and have local regression coverage.
Hosted provisioning, backup/restore drill, connector ownership recovery and
native linguistic approval still block a production claim or deployment. The
content candidate `foundation-2026.07.3` remains unpromoted and has no
linguistic approval.
